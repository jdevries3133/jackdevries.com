# Git Roadmap

This is a git guide for anyone. You don't need to be a programmer, or know what
git is - I'll tell you! Git is one of my favorite technologies. I consider
myself to be pretty scatter-brained, disorganized, and easily distractible. But
I also think I'm a pretty good software engineer. Git is the most important tool
which closes the gap between these two aspects of myself. _It's that powerful._

So, what is git? If you don't know, I'm not going to tell you yet; sorry. First,
we need to talk about plain text. If you know about git or you're a programmer,
have a look at my post on [plain text](./plainText) first!

Git can be useful to you whether or not you're programming. This post is a
_complete_ git roadmap. I'll start by talking to a totally general non-technical
audience, which requires a side-quest into the discussion of our modern
walled-garden software ecosystem versus the older and freer Unix ecosystem where
everything was just text. If you're not a programmer, why should you care about
git? You probably don't even know what it is! In addition to programming, I use
git for personal finance, notes, technical documents, graphs/charts/tables, and
other writing content. The blog post you're reading now is tracked in a git
repository, alongside the code for this website. That being said, you can't use
git to track, for example, a Microsoft Word document. Technically, you can – any
data can be tracked in a git repository – but first and foremost git is intended
to be used with plain text.

Yes, plain text. The stuff with the ugly square letters that you may have last
thought about when you opened Notepad++ in your elementary school computer lab.
The stuff in `.txt` files. The stuff that doesn't have headings, **bold**,
_italic_, tables, [links](https://example.com), or any features whatsoever
except for being able to capture the exact buttons you press on the keyboard and
then letting you change them later.

I might be losing you at this point, but stick with me. If plain text doesn't
excite you, it's very possible that you don't know what you're missing out on;
and I'd like to try to elucidate.

# OK, What is Git?

Thank you for making it to the crux of my TED talk; let's finally get to the
point. Git solves a few problems from the vignette before. Specifically;

- _Am I supposed to put all my information into a bunch of `.txt` files in
  random places on my computer? That sounds like an absolute disorganized mess!_
- _I won't be able to keep track of changes_.
- _If I accidentally the wrong file or folder, I'll lose important data._

[git](https://git-scm.com/) is version control software for plain text
documents. It can be used for code, notes, technical documents, or anything else
that you store as plain text including structured data in JSON, yaml, or toml
files.

## The Unix Philosophy

As you move your information diet from closed-garden platforms into plain text,
you'll notice that the software you use becomes smaller, more focused, deeper in
functionality, and often free. This phenomenon is described as the [Unix
Philosophy](https://en.wikipedia.org/wiki/Unix_philosophy). The goal here is for
a constellation of programs to work together to do a job, using plain text as a
universal interface. For example;

- you edit your document in VS Code
- you keep track of changes over time with git
- you share your work and collaborate on a git hosting provider like GitHub,
  GitLab, etc.
- you turn your document into a nice-looking shareable PDF using
  [pandoc](https://pandoc.org/MANUAL.html)

Git is probably the most important component to me, and it's useful if you want
to try getting started with applying this philosophy.

# Level 1: Solo & Local

You want to dip your toes into using git to keep track of information. You might
not be programming at all. Maybe your only git use-case is for keeping track of
notes or a personal finance ledger. Or you might have a few python scripts to
keep track of; you're not doing heavy-duty software engineering. Another great
level 1 use-case is keeping track of configuration files. This use-case is
sometimes called a dotfiles repo.

## Level 1 Commands

```bash
git init
```

In an empty folder, run this command to create a new git repository. This
creates a hidden `.git` folder.

You can choose the scope of a git repository. At many companies, all of the
code, testing scripts, production system configuration, internal docs, and
external docs often live in one single gigantic git repository. Git repos can
scale to mind-boggling scales. The Linux kernel is a very large and well-known
repo. It has 88,000 files today and 1,351,445 historical revisions! Or, you can
create a tiny repository. For example, you could create a repository to store
your notes on a book you're reading, which might only ever have a handful of
files.

Whatever the repo is for, a good thing to do first is to create a `README.txt`
(or `README.md` if you want to use markdown) file in the repository's folder. In
this file, say what the repository is for. This file can contain just a single
sentence if you don't have much to say. Create this file using your text editor
of choice.

Now, this brings us to our next command;

```bash
git status
```

You will see the following output if you've been following along;

```
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        README.md

nothing added to commit but untracked files present (use "git add" to track)
```

Forget about `git add` - you don't need that yet.

The next thing we need to do is to create our first git commit. "Commit," is
like "save." Every time you commit, a backup of your work is stored in the
`.git` folder, and you create a new revision.
